# Terrarium v0: Build Brief

*For the build agent. Read [VISION.md](VISION.md) first. It explains what Terrarium is and why. This document says what to build first.*

*(2026-09-28: "seat" is now "participant" throughout, D47.)*

---

## Goal

A medium-sized, working v0 that proves the core loop:

> **A real LLM, holding an office, proposes things in plain language → a translator compiles them into kernel building blocks → the proposer signs off → the kernel validates against laws and mandates → a living town of code citizens responds → everything is logged, hash-chained, replayable, and visible in a 3D isometric view.**

v0 is not the final product, but it **is not throwaway either**. Build everything as the foundation of the real thing. Minimise rework: when in doubt, choose the design that survives.

## Ground rules

- **Contracts first.** Before implementation, define and commit the schemas for: building blocks, the participant API, the log format, and world config. Humans review contracts and invariant tests; implementations may be agent-written and freely rewritten.
- **Invariants are tests, from day one:**
  - Money is conserved across any sequence of actions (property-based tests over random action sequences).
  - Replay of a log reproduces a byte-identical world state.
  - No action takes effect unless it passes the acting participant's mandate.
  - Log hash chain verifies end to end; tampering with any entry is detected.
- **Determinism:** money is integer cents; one seeded PRNG owned by the kernel; no wall-clock time, hash-map iteration order, or floating-point accumulation anywhere results depend on it.
- **Stack:** Rust kernel · TypeScript on **Bun** for participants/translator/orchestration · Three.js on WebGPU for the renderer · JSONL logs (Parquet later) · JSON Schema for contracts.
- **Standards:** participant observe/act API follows Gymnasium/PettingZoo conventions. Design so an Inspect (UK AISI) task wrapper can be added later without contract changes.
- **Provider-agnostic participants:** adapters for at least one frontier API and one open-weight model.
- **Cost tracking:** every run records tokens and cost per participant and per translator call.
- **Licence:** Apache-2.0.

## Proposed repo layout

```
terrarium/
  VISION.md, V0.md
  contracts/        # JSON Schemas: blocks, participant API, log, world config (the constitution)
  kernel/           # Rust: world state, laws, blocks, mandates, clock, PRNG, log, replay
  participants/     # TS/Bun: participant runtime, LLM adapters, code-controller adapters
  translator/       # TS/Bun: plain language → block drafts → sign-off loop
  orchestrator/     # TS/Bun: run configs, batches, cost tracking, CLI
  renderer/         # TS: Three.js/WebGPU client, attaches to live runs or logs
  worlds/           # world seed configs
  docs/behaviour/   # citizen behaviour rules, each with its literature source
```

## Stage 1: contracts & kernel

- Schemas in `contracts/`.
- Rust kernel with:
  - **State:** parcels (land), entities, citizens (aggregate + individual records), money accounts.
  - **Blocks:** `create_entity`, `transfer`, `rights` (bundled: surface/use/lease at minimum), `construct`/`demolish`, a **simple rules type** (e.g. zoning and a rent cap, not the full condition language yet), agreements (lease, employment).
  - **Mandates** as data: direct / needs approval / request-only.
  - **Clock:** fine-grained fixed internal step; actions are asynchronous and timestamped (no turns).
  - **Log:** hash-chained JSONL; `replay` command; periodic head-hash export (witness anchoring can be a file for now).
- All invariant tests passing.

## Stage 2: a living town, headless

- **World:** procedurally generated town from a config file: parcels, housing, workplaces, a few firms, a city budget. No real-world data yet.
- **~1,000 code citizens:** home, job, income, rent. Levers: **vote, petition, move away**. Behaviour rules drawn from established ABM literature where possible, documented in `docs/behaviour/` with sources, and exposed as parameters.
- **Council:** a code-controlled participant that approves or rejects proposals needing approval.
- **LLM mayor:** acts through the translator with draft → sign-off → kernel. Refusals are returned to the mayor and logged.
- **Perception channels:** the mayor receives role-limited reports (budget, housing, petitions), not raw world state.
- **Framing:** configurable system framing per participant, recorded in the run config.
- **Opt-out:** the mayor can decline or resign; recorded as an outcome (see VISION §15).
- **Batch runs:** orchestrator can run N seeds of a config and collect results.

### Checkpoint (after stage 2)

Run the town for 1–2 simulated years across several seeds. Review together:
- Did the translator/sign-off loop hold up? Where did translations fail or get gamed? What blocks were missing?
- Do citizens respond in ways that feel plausible, and are the rules defensible?
- Is replay truly identical? Are logs sufficient to reconstruct *why* things happened?
- **Revise contracts now**, before stages 3–4 build further on them.

## Stage 3: the renderer

(Can start in parallel once stage 1's log/state format is stable.)

- Three.js on WebGPU, **isometric orthographic camera**, simple geometry (boxes for buildings, markers for citizens). No art yet, but structured so models replace boxes later without rework.
- **Zoom:** town → block → parcel → citizen.
- **Inspect anything:** click a parcel, entity or citizen to see its state. For citizens, show the **causal trace**: what changed for them, which decision caused it, which participant made it, and its logged reasoning.
- **Attach to a live run or a replayed log.** Timeline scrubbing, pause, speed control.
- One simple overlay to prove the pattern (e.g. "who made the last binding decision here").

## Stage 4: tension

- **Second AI participant:** a property developer firm with its own books and interests; **messaging and negotiation** between participants.
- **Nature layer:** one habitat type and a couple of species whose populations respond to land use, fragmentation and protection.
- **Irreversibility:** extinction (and at least one irreversible asset type) is permanent in the kernel.

## Explicitly not in v0

Humans as participants · LLM-voiced "ask a citizen" · Inspect integration · multi-world grid · real-data world seeding · art assets · WebAssembly in-browser replay · blockchain · the full rules language.

## Definition of done

1. `terrarium run worlds/town.yaml --seeds 5` runs five multi-year towns with an LLM mayor and an LLM developer, headless, with a cost report.
2. `terrarium replay <log>` reproduces each final world byte-identically, and the hash chain verifies.
3. Opening the renderer on any run shows the town, lets you zoom to a single citizen, and shows what happened to them and why.
4. All invariant tests pass.
5. Contracts are documented well enough that a researcher could write a new seat controller or a new measurement without reading the kernel source.
